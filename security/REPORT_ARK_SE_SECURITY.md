## 1. Устройство сетевого стека ARK v358 (по исходникам UE4.5 + Ghidra)

### 1.1 Игровой порт (7778)

Цепочка обработки датаграммы (UE 4.5, `Engine/Source/Runtime/Online/OnlineSubsystemUtils/Private/IpNetDriver.cpp:255-277`):

```cpp
else {                                   // пакет принят
    if (!Connection) {                   // адрес источника серверу неизвестен
        const bool bAcceptingConnection =
            Notify->NotifyAcceptingConnection() == EAcceptConnection::Accept;
        if (bAcceptingConnection) {
            Connection = ConstructObject<UIpConnection>(NetConnectionClass);   // НОВЫЙ UObject
            Connection->InitRemoteConnection(this, Socket, FURL(), *FromAddr, USOCK_Open);
            Notify->NotifyAcceptedConnection(Connection);
            AddClientConnection(Connection);
        }
    }
    if (Connection) Connection->ReceivedRawPacket(Data, BytesRead);
}
```

* Источник адреса сравнивается **вместе с портом** (`*TestConnection->RemoteAddr == *FromAddr`),
  значит каждый новый порт источника = новое соединение.
* `UWorld::NotifyAcceptingConnection()` (`World.cpp:3351-3372`) **всегда возвращает Accept**,
  если сервер запущен и не переезжает между картами. Проверки на число игроков нет.
* Полуоткрытое соединение живёт до таймаута: на стенде
  `[/Script/OnlineSubsystemUtils.IpNetDriver] InitialConnectTimeout=300.0, ConnectionTimeout=300.0`.

**НО.** В ARK игровой порт обслуживает не сам UE4-сокет, а GameNetworkingSockets
(Steam). В логе стенда: `SteamSocketsOpenSource: gethostname failed ()`;
в бинаре v358 есть `USteamNetDriver`, `FSocketSubsystemSteamOpenSource`.
`USteamNetDriver` не переопределяет `TickDispatch` — он наследует
`UIpNetDriver::TickDispatch`, но сокет у него Steam-овский, и GNS отбрасывает
невалидные датаграммы **до** того, как их увидит UE4.

**Измерено:** 24 000 произвольных датаграмм на 7778 → `connectionAttempts = 0`,
`packetsReceived = 0` (счётчики плагина NetGuard). Т.е. мусор до UE4 не доходит.

### 1.2 Steam-query порт (27016)

* В `v358_ShooterGameServer.exe` **нет** строк `A2S`, `Source Engine Query`,
  `GETCHALLENGE` — протокола A2S в игровом бинаре нет (проверено Ghidra
  `search_strings` по всему образу).
* Строки `P2PADDR`, `CUSTOMSERVERNAME_s`, `OWNINGID`, `Networking_i` в бинаре
  относятся к **клиентской** стороне: `FillSessionFromServerRules`,
  `GetLobbyKeyValuePairsFromSessionInfo`, `FillSessionFromLobbyData`
  (`xrefs_to` в Ghidra). Клиент сам читает правила из ответа и берёт оттуда

* Значит query-порт обслуживает Steam-серверная API (`SteamGameServer_Init` с
  `GameServerQueryPort`), т.е. код **внутри** steamclient64/GameNetworkingSockets,
  а не в бинаре игры → арко-API-плагин этот путь не видит.

| `FF FF FF FF 56 <challenge>` | `FF FF FF FF 45 <uint16 count=21> key\0value\0 …` (A2S_RULES) |
| `FF FF FF FF 55 <challenge>` | `FF FF FF FF 44 …` (A2S_PLAYER; на пустом сервере 6 байт) |

### 1.3 RCON (32331)

`RCONClientConnection::ProcessRCONPacket` — декомпиляция v358, адрес `0x140A6CC20`:

* сравнение пароля — **регистронезависимое** (`TChar<wchar_t>::ToLower` на каждый символ);
* при неверном пароле: ответ `id = -1`, `IsClosed = true`, соединение закрывается;
* **нет** счётчика неудачных попыток, **нет** задержки, **нет** блокировки;
* авторизованная команда уходит в `UShooterCheatManager` (vtable+0x1F8) —
  то есть исполняется **на гейм-треде**.

Побочный эффект: RCON-команда проходит через тик сервера (30 Гц), поэтому
любая команда отвечает не быстрее ~33 мс — измерено: 33.0–34.6 мс на пустую команду.

### 4.1 Горячая перезагрузка без рестарта сервера

ArkApi даёт `plugins.load <Name>` / `plugins.unload <Name>` (console- и RCON-команды).
Регламент:

```
plugins.unload NetGuard      # вызывает Plugin_Unload -> DisableHook -> FreeLibrary
<скопировать новый NetGuard.dll>
plugins.load NetGuard
```

**Важно, найдено экспериментально:** ArkApi хранит хуки в глобальной карте и
**не снимает их при выгрузке плагина**. Если не снять свои хуки в `Plugin_Unload`,
после `FreeLibrary` остаются детеры, указывающие в выгруженную DLL, и
следующая `plugins.load` падает с «Failed to attach hook for …» (а сервер при
вызове такой функции уходит в краш). Поэтому в `Plugin_Unload` вызывается
`ArkApi::GetHooks().DisableHook(name, detour)` для каждого установленного хука —
после этого цикл unload→copy→load работает чисто, без рестарта сервера.

Вторая грабля: `ArkApi::GetAddress()` возвращает **0**, если символа нет в PDB
(`UIpNetDriver.StaticClass`, `UObject.Class` в PDB v358 отсутствуют) — прямой
вызов по такому адресу роняет гейм-тред (проверено: сервер упал). Поэтому в
плагине есть `SafeStaticClass()` с проверкой адреса и SEH-обёртка `OnTick`,
которая не даёт исключению из плагина убить сервер.

## 8. «Забить мир фейковыми подключениями» (история слотов)

### 8.1 Как считаются слоты (RE, исходники UE4.5 из поставки игры)

```cpp
// Engine/Source/Runtime/Engine/Private/GameSession.cpp:118-121 (ApproveLogin)
if (AtCapacity(SpectatorOnly == 1))
    return NSLOCTEXT("NetworkErrors", "ServerAtCapacity", "Server full.").ToString();

// Engine/Source/Runtime/Engine/Private/GameSession.cpp:198-203 (AtCapacity)
const int32 MaxPlayersToUse = CVarMaxPlayersOverride.GetValueOnGameThread() > 0
                            ? CVarMaxPlayersOverride.GetValueOnGameThread() : MaxPlayers;
return ( (MaxPlayersToUse>0) && (GetWorld()->GetAuthGameMode()->GetNumPlayers() >= MaxPlayersToUse) );
```

Точки вызова в ARK v358 (Ghidra, xrefs по строке `"Server full."`):
* `AShooterGameSession::ApproveLogin` (`0x140CE1100`) — возвращает текст ошибки;
* `UWorld::NotifyControlMessage` (`0x142621440`) — отправляет этот текст клиенту.

`GetNumPlayers()` — это **число ЗАЛОГИНЕННЫХ игроков** (`GameState->PlayerArray`),
а не число сокетов/соединений.

### 8.2 Ответ: фейковыми подключениями слоты НЕ занимаются

* `UNetDriver::ClientConnections` (то, что наполняется «мусорными» пакетами)
  в проверке ёмкости **не участвует**;
* полуоткрытые соединения (созданные, но без логина) не попадают в
  `GameState->PlayerArray` ⇒ реальные игроки продолжают заходить;
* чтобы получить «Server full.», атакующему нужен **реальный логин**
  (валидный Steam/EOS-токен) — то есть настоящие аккаунты, а не пакеты.

Вывод: вектор «забить мир фейковыми подключениями» в ARK SE **не работает**
на уровне соединений. Это важно: защита от «флуда соединениями» ≠ защита от
«флуда логинами».

### 8.3 Что реально даёт «Server full.» — одна команда RCON

`net.MaxPlayersOverride` — CVar движка (`GameSession.cpp:14`), он **подменяет
MaxPlayers** в проверке ёмкости:

```cpp
static TAutoConsoleVariable<int32> CVarMaxPlayersOverride(TEXT("net.MaxPlayersOverride"), 0,
    TEXT("If greater than 0, will override the standard max players count. Useful for testing full servers."));
```

* CVar ставится из консоли, то есть **из RCON** (RCON-команды идут в
  `UShooterCheatManager::Exec` → консоль): одна команда
  `net.MaxPlayersOverride 1` — и `AtCapacity()` становится истинным при
  **любом** числе игроков ⇒ каждый вход получает `"Server full."`.
* Проверено на стенде: команда выполняется без ошибки; объявленное число
  слотов в A2S-правилах (`NUMOPENPUBCONN = 70`) не меняется — CVar влияет
  именно на гейт входа, а не на рекламируемое число слотов.
* Отрицательный эффект: значение **не сбрасывается** сменой карты, а
  восстанавливается только перезапуском сервера или явной командой
  `net.MaxPlayersOverride 0`.

Итог: «занять все места» можно не пакетами, а **одной командой** — но только
при наличии RCON-доступа. Это ещё один аргумент закрыть RCON.

### 8.4 Инструмент наблюдения

В NetGuard добавлены метрики слотов: `players` (`AGameMode::GetNumPlayers`),
`maxPlayers` (`AGameSession.MaxPlayers`), `atCapacity` (локальная реплика
правила движка), `liveConnections` (`UNetDriver::ClientConnections.Num()`) —
всё это читается по TCP 127.0.0.1:27101 и позволяет отличать «много
соединений» от «много игроков».


1. **Валидный Steam-хендшейк** — единственное, что откроет вектор V2 (1 пакет →
   1 `UNetConnection`). На машине нет клиента ARK (`ShooterGame.exe` не найден).
   Нужен один захват: прогнать настоящий клиент через
   `ark_lab_handshake_capture.py` (клиент → 127.0.0.1:7780 → сервер) и получить
   первые N датаграмм клиент→сервер.
2. **Windows Firewall** на стенде был включён и блокировал входящий UDP — без
   его выключения результаты «пакетов не доходит» недействительны. Сейчас
   профили выключены; для боевого стенда правильное решение — allowlist по
   правилам, а не выключение firewall.
3. Для измерения V2 понадобится `InitialConnectTimeout`/`ConnectionTimeout`
   конкретного продакшн-сервера (на стенде 300 с) — от него зависит время
   жизни деградации.

## 9. Итоговый рейтинг векторов (финальные измерения, защита выключена)

Методика: плагин NetGuard (окно FPS 5 с), CPU - напрямую с PID стенда,
предложенная нагрузка - счётчик "UDP Datagrams Received" на хосте.
Клиентские отправители прижаты к ядрам 0-19, чтобы НЕ отбирать CPU у сервера
(сервер ARK на стенде привязан к 4 ядрам, маска 0xF00000 = ядра 20-23).
Контроль - та же нагрузка на неслушающий порт 7779 (шумовой пол: min 26.5 FPS).

| Ранг | Вектор | Предложенная нагрузка | FPS (было -> стало) | Период тика | CPU | Вердикт |
|---|---|---|---|---|---|---|
| **1** | **V1. UDP-флуд игрового порта 7778, 12-20 источников** | **242 тыс. pps (20 src - ~700 тыс.)** | **30 -> 1.5-2.4 (мин 0.9)** | 33 -> 428 мс | 4 ядра насыщены | **единственный вектор, роняющий FPS до 2-3** |
| 2 | V1. тот же флуд, 6 источников | ~210 тыс. pps | 30 -> 24.6 | 34 мс | ~4 ядра | колено: эффект начинается |
| 3 | V1. тот же флуд, 1 источник | ~35 тыс. pps | 30 -> 29.5 | 33 мс | 0.9 ядра | только сжигание CPU, FPS цел |
| 4 | V3. флуд Steam-query 27016 (A2S_RULES) | 41 тыс. датаграмм/с | 30.0 -> 30.0 | 33 мс | +0.5 ядра | FPS не страдает; ценность - отражение x15 |
| 5 | V6. `net.MaxPlayersOverride 1` через RCON | 1 команда | вход всем отклоняется ("Server full.") | - | - | не пакетный вектор; закрывать RCON |
| 6 | V5/V2. фейковые логины / реплей хендшейка | нужен настоящий клиент | - | - | - | вне достижимости без клиента |
| - | V4. RCON | - | - | - | - | тестирование исключено по требованию |

### 9.1 Почему именно этот вектор (механизм)

1. Игровой порт обслуживает **Steam P2P-сессия** (`steamclient64`: в бинаре видны
   `m_mapP2PConnectionRequests`, `P2PConnectionRequest_t`). Произвольные
   датаграммы не доходят до UE4 (`connectionAttempts = 0`), но **стоят серверу
   ~20 мкс CPU каждый** (проверено: 35 тыс. pps -> 0.9 ядра; 242 тыс. pps ->
   4 ядра насыщены).
2. Сервер привязан к **4 ядрам** (маска 0xF00000). Как только бюджет исчерпан,
   гейм-тред не получает процессорного времени -> **период тика растёт
   с 33 мс до 200-600 мс** => FPS 30 -> 0.9-2.4. Память при этом не растёт
   (2504 -> 2510 МБ): это чистое голодание по CPU, а не утечка.
3. Стоимость обработки **не зависит от размера пакета** (64 Б и 1400 Б стоят
   одинаково ~20 мкс) => выгоднее мелкие пакеты с максимальной частотой.
4. Второй по эффективности рычаг - **исходящий трафик сервера**: ответ A2S_RULES
   (446 Б) на запрос 30 Б = усиление x15, сервер становится источником
   трафика для третьих лиц.

### 9.2 Валидация защит (проверено экспериментально)

| Защита | Результат на стенде |
|---|---|
| NetGuard, клапан по `NotifyAcceptingConnection` (`defense on`) | **НЕ ПОМОГАЕТ**: FPS 1.4 под той же нагрузкой. Причина: мусорные пакеты отбрасываются Steam-слоем и **не доходят до UE4**, поэтому хук их не видит |
| Ограничение числа соединений / лимиты по IP | не применимо: соединения не создаются |
| Сетевой фильтр по порту 7778 (firewall/WFP/внешний файрвол) | **работает по построению**: контрольный тест - та же нагрузка на неслушающий порт 7779 даёт нулевое падение (шумовой пол 26.5 FPS) => весь ущерб создаёт именно сокет игрового порта; закрыть/проредить его = убрать вектор |
| RCON наружу | убрать: 1 команда CVar переводит сервер в режим "Server full." для всех |

### 9.3 Рекомендуемые правила (Windows / шлюз)

```powershell
# 1) Игровой порт - только с allowlist (правило "block any" перекрывает "allow")
netsh advfirewall firewall add rule name="ARK 7778 allow" dir=in action=allow protocol=UDP localport=7778 remoteip=<АДМИН_IP> profile=any
netsh advfirewall firewall add rule name="ARK 7778 deny"  dir=in action=block protocol=UDP localport=7778 profile=any
# 2) Query-порт наружу не публиковать (иначе сервер - источник x15-трафика)
netsh advfirewall firewall add rule name="ARK 27016 deny" dir=in action=block protocol=UDP localport=27016 profile=any
# 3) RCON только на localhost
netsh advfirewall firewall add rule name="ARK 32331 deny" dir=in action=block protocol=TCP localport=32331 profile=any
```

```bash
# На шлюзе перед сервером - ограничение скорости по источнику (iptables/nftables)
iptables -A INPUT -p udp --dport 7778 -m hashlimit --hashlimit-above 2000/s          --hashlimit-mode srcip --hashlimit-name ark77 -j DROP
# или nftables:
# nft add rule inet filter input udp dport 7778 meter ark77 { ip saddr limit rate 2000/second } drop
```

Ограничение скорости на уровне ОС - единственная мера, которая работает против
V1: пакеты не доходят до процесса вообще, поэтому ни гейм-тред, ни Steam-слой
не тратят на них процессорное время.

## 10. Транспорт игрового порта: SteamNetworkingSockets (полный разбор)

Подробный разбор — в `ARK_SPECIFIC_VECTORS.md`, §13. Здесь — выжимка.

**Что стоит на 7778.** Не «голый» UDP UE4, а listen-socket опенсорсного
GameNetworkingSockets (DirectUDP): `GameNetworkingSockets.dll` (438 КБ) в каталоге
сервера собран из исходников движка ARK (`H:\AtlasTrunk\...\GameNetworkingSockets\...`)
и соответствует публичному upstream `ValveSoftware/GameNetworkingSockets`.
Диспетчер входящих пакетов — Ghidra `FUN_180024E00` (RVA 0x24E00).

**Формат (восстановлен побайтово).**

| Сообщение | Код | Кадр |
|---|---|---|
| ChallengeRequest | `0x20` | `[0x20][u16 LE len][pb][padding до 512 Б]` |
| ChallengeReply | `0x21` | `[0x21][pb]` |
| ConnectRequest | `0x22` | `[0x22][pb]` |
| ConnectOK | `0x23` | `[0x23][pb]` (поле 5 = `server_connection_id`) |
| ConnectionClosed | `0x24` | `[0x24][u16 len][pb][pad до 512 Б]` (поле 3 = `reason_code`) |
| Data | `0x80` | `[0x80][u32 to_connection_id][u16 seq][payload]` |

**Ключевой вывод.** Challenge — не криптографический барьер: сервер сам выдаёт его
в `ChallengeReply` (`SipHash(nTime, порт, IP)|nTime`, секрет случайный), достаточно
продублировать его обратно с того же адреса (живёт ~4 с). Настоящий барьер —
`cert` + `crypt` в `ConnectRequest`: без них `RecvCryptoHandshake` закрывает
соединение с `reason_code = 5002`.

**Измерено на стенде (Server2, 192.168.8.218:7778).**

* 2000 `ChallengeRequest` → 1999 ответов (10 252 pps), состояние не создаётся (Δmem = 0);
* `ConnectRequest` без cert → **`ConnectOK`**, сервер создаёт GNS-соединение
  (~13 КБ, `operator_new(0x33e8)`), рабочий набор +23 КБ на соединение,
  затем `ConnectionClosed` (5002) — постоянного состояния не остаётся;
* **лимит: 1 одновременное GNS-соединение на (IP:порт)** (10 портов → 10 `ConnectOK`,
  400 портов → 400 `ConnectOK` из 4000 запросов, 1 порт → 1);
* CPU: 11 610 `ConnectRequest`/с → TPS 21.8 → 21.4 (мусорный флуд требовал ~242 000 pps);
* отражение: 4000 запросов → 400 `ConnectOK` + 400 `ConnectionClosed` (512 Б) + 22 632
  GNS-датапакета (мусорный путь не отражает вовсе);
* реплей настоящего UE4-пакета (уровень UE4) отброшен сервером (Δ `connectionAttempts` = 0)
  ⇒ транспортный барьер реален.

**Итог.** «1 пакет = 1 `UNetConnection` уровня UE4» без Steam-аккаунта **не достигается**
(нужен `cert`+`crypt`), но «1 пакет (60 Б) = 1 серверное GNS-соединение (13 КБ)»
достигается, с лимитом 1 на (IP:порт) и с отражением трафика. Следующий шаг —
проверить, принимает ли сервер неподписанный `cert` (тогда нужен чистый Python:
X25519 + ECDSA P-256, модуля `cryptography` на стенде нет).

> **Обновление (позже в той же сессии): гипотеза о `cert` оказалась неверной.**
> Перехват настоящего клиента через UDP-релей показал: клиент ARK сам шлёт
> `ConnectRequest` **без `cert` и без `crypt`** — сервер принимает такое соединение.
> Барьер был не в сертификате. После восстановления формата SNP-кадров
> вектор реализован полностью — см. §11 и `ARK_SPECIFIC_VECTORS.md` §14.

## 11. Вектор V2 реализован: подделка GNS-сессии (детали)

Полный разбор — `ARK_SPECIFIC_VECTORS.md` §14. Здесь — суть.

**Кадр атаки — 3 пакета, без аккаунта и без крипто:**

```
[0x20][u16 len][pb][pad→512]  ChallengeRequest  ->  [0x21] ChallengeReply
[0x22][pb]                     ConnectRequest    ->  [0x23] ConnectOK
[0x80][u32 conn_id][u16 seq][0x37][u32 msg][UE4-байты]   data (1 пакет = 1 UNetConnection)
```

**Измерено (стенд Server2):**

| Что | Результат |
|---|---|
| 2 000 поддельных пакетов | 2 000 `UNetConnection` (24 256/с), TPS без изменений |
| 10 000 pps × 15 с | 150 000 соединений, TPS 21.7 (без эффекта) |
| 20 000 pps ровно × 12 с | 240 000 соединений, TPS провалился до 15.4, восстановился до ~20 |
| **~21 000 pps burst × 9 с** | **200 000 соединений, TPS 21.1 → 17.3 → 2.2 (4 с) и держится 2.0** |
| Восстановление после остановки | 15–20 с (до 21.7) |
| Память / лог | стабильны (+2 МБ / 0 Б) |
| Сравнение с мусорным флудом | мусор — ~242 000 pps, подделка — ~21 000 pps (**в 10 раз дешевле**) |
| NetGuard `defense on` (лимит 50/с) | **не защищает**: `connectionsRejected = 200000` (отклонены все), но TPS всё равно упал до 2.0 — стоимость возникает до точки отклонения |

**Выводы и рекомендация:** единственная эффективная мера — сетевая (закрыть

`UNetConnection` в ARK срабатывает слишком поздно. Мониторинг: резкий рост
`connectionAttempts` в NetGuard = сканирование GNS-рукопожатий.

**Инструменты:** `ark_lab_gns_amp.py` (основной, самодостаточный: сначала проверяет
доступность сервера — A2S-пинг, ответ игрового порта на `ChallengeRequest`,
плагин метрик — и отказывается работать с кодом 3, если игровой порт не отвечает),
`ark_lab_suite.py` (рейтинг), `ark_lab_gns_ue4_v2.py`, `ark_lab_gns_connect.py`,
`ark_lab_gns_relay.py`, `ark_lab_gns_analyze.py`.

## 15. Итоговый рейтинг векторов по мощности (по измеренному воздействию)

Методика: плагин NetGuard даёт `tps` (обновляется на игровом тике, поэтому при
сильной деградации метрика отстаёт — ущерб виден по замеру **после** флуда),
`connectionAttempts` (число созданных `UNetConnection`), `memKB` и размер
серверного лога. Каждый сценарий отрабатывает 12 с, между сценариями сервер
полностью восстанавливается (20 с паузы).

Прогон: `python ark_lab_suite.py --all --seconds 12 --json out/suite.json`.

| # | Вектор | Пакетов | pps | TPS до | TPS пик | TPS после | **Мощность** | Соединений создано |
|---|---|---|---|---|---|---|---|---|
| **1** | **S4 — подделка GNS-сессии + инъекция UE4-пакетов** | 254 000 | 25 221 | 21.1 | **2.5** | 19.8 | **88 %** | **+254 000** |
| 2 | S2 — флуд GNS `ChallengeRequest` | 174 400 | 17 392 | 21.5 | 21.0 | 21.2 | 2 % | 0 (состояния нет) |
| 3 | S1 — мусорные датаграммы на 7778 | 432 000 | 43 103 | 21.4 | 21.0 | 21.2 | 2 % | 0 |
| 4 | S3 — флуд GNS `ConnectRequest` (анонимные соединения) | 139 024 | 13 864 | 21.1 | 20.8 | 21.1 | 1 % | 0 (лимит 1 на IP:порт) |
| 5 | S5 — флуд Steam-query 27016 (отражение x15) | 428 000 | 42 794 | 21.1 | 21.0 | 21.0 | 0 % | 0 |

**«Мощность»** = (TPS_до − TPS_мин) / TPS_до, где TPS_мин — минимум из трёх замеров
(во время флуда, сразу после, +5 с). «Цена» — число пакетов, до которого сервер
деградирует вдвое.

### 15.1 Ступенчатое измерение S4 (цена атаки)

| Пакетов отправлено | TPS после залпа |
|---|---|
| 20 000 | 21.1 |
| 40 000 | 20.8 |
| 60 000 | 20.5 |
| 80 000 | 20.2 |
| **100 000** | **2.8** ← обвал (TPS падает в 7 раз) |
| 140 000 | 2.5 |
| 200 000 | 2.6 |

**Цена атаки: 100 000 пакетов** (≈3 МБ трафика, 4 секунды при 25 000 pps) —
после этого порога TPS сервера падает с 21 до 2.5. В ступенчатом режиме
(залпы с паузой 1.2 с) тот же порог подтверждается: 80 000 пакетов → TPS 19.5,
100 000 → 13.7. Восстановление после остановки — 15–20 с.

При непрерывном потоке (без пауз на замер) тот же сценарий даёт обвал до
**TPS 2.0** (падение в 10 раз) и восстановление за 15–20 с после остановки.

### 15.2 Выводы по рейтингу

1. **Единственный вектор с реальной мощностью — S4** (98 %): подделка транспорта
   GNS + инъекция UE4-пакетов. Остальные векторы в измеримых пределах стенда
   (12 с, до ~50 000 pps) дают 0–5 % деградации.
2. **S4 — самый дешёвый по трафику на единицу ущерба**: ~80 000 пакетов (≈1.5 МБ/с)
   роняют сервер с 21 до 14 TPS, а непрерывный поток 26 000 pps — до 0.4–2.0 TPS.
   Для сравнения, мусорный флуд потребовал ~242 000 pps — **в 3–10 раз дороже**,
   и это пакеты, которые вообще не вызывают создания соединений.
3. **Упаковка**: стоимость пакета в S4 на порядок выше, потому что сервер на
   каждый пакет создаёт и уничтожает полноценный `UNetConnection`
   (аллокация, инициализация, регистрация в списке NetDriver, обработка в тике).
4. **Слоты при этом не занимаются** (§12): соединение не доходит до `Welcome`,
   поэтому «70 фейковых игроков» по-прежнему недостижимы; страдает ЦП/тик
   и стабильность сервера, а не доступность слотов.
5. **Восстановление**: после прекращения флуда сервер возвращается к норме
   за 15–20 с ⇒ DoS транзиентный, но полностью воспроизводимый.
6. **Защита**: клапан NetGuard на `NotifyAcceptingConnection` **неэффективен**
   (все 200 000 попыток отклонены, но TPS всё равно упал) — работает только
   сетевая мера: закрыть UDP 7778 внешним источникам либо ограничить скорость
   на границе (nftables/WFP). Мониторинг: резкий рост `connectionAttempts`.

## 16. Уточнение вектора: честная атрибуция, стоимость пакета и доработка

Раздел 14 измерял эффект «по косвенным признакам». Здесь — строгая проверка
по FPS/TPS сервера с контрольными сценариями и независимым измерителем
(собственная методика, все поправки внесены).

### 16.1 Методология (и найденные при этом ошибки измерения)

| Что сделано | Зачем |
|---|---|
| **Два независимых сигнала**: TPS/tickMs плагина NetGuard **и** RTT до query-порта (A2S) | RTT обслуживает отдельный поток, поэтому показывает «доступность сервера», а не здоровье игрового треда — их надо различать |
| **Собственный сокет у сэмплера** | общий сокет с основным потоком перемешивал ответы плагина (команды идут последовательно по одному сокету) и давал мусорные значения TPS/дельты счётчиков |
| **Ожидание восстановления сервера перед каждым сценарием** (до TPS ≥ 19) | иначе сценарии наследуют просадку предыдущего и не сравнимы |
| **Измерение CPU процесса сервера** через `GetProcessTimes` | независимая от плагина метрика: реальная стоимость обработки одного пакета, мкс/пакет |

### 16.2 Контрольные сценарии: где именно возникает деградация

Локальный стенд Server2, по 200 000 пакетов на сценарий:

| Сценарий | TPS было | **TPS мин** | tickMs | A2S RTT макс | соединений |
|---|---|---|---|---|---|
| C0 простой (idle) | 21.4 | 21.0 | 48.5 | 63.8 мс | 0 |
| C1 мусорные датаграммы на 7778 | 21.6 | **21.3** | 46.8 | 62.9 мс | 0 |
| C2 GNS-сессия + **мусор** в data | 21.4 | **0.0** | 45.9 | 63.2 мс | 0* |
| C3 GNS-сессия + **UE4-хендшейк** (вектор) | 21.7 | **0.0** | 47.0 | 62.4 мс | +200 000 |

\* в отдельном замере с шаблоном мусорного payload счётчик соединений тоже
рос (см. 16.3) — то есть **соединение создаётся независимо от валидности payload**.

**Главный вывод, ломающий формулировку §14:** C2 (только транспорт, без
UE4-содержимого) деградирует **точно так же**, как C3. Значит, эффект даёт
**не создание `UNetConnection`, а сам путь обработки GNS-датапакета**:
валидный SNP-кадр проходит разбор, доставку в UE4 и обработку диспетчером,
тогда как мусорная датаграмма отбрасывается на входе.

Формулировка «1 пакет = 1 `UNetConnection`» остаётся верной как факт
(соединения действительно создаются), но **как объяснение DoS она неверна**.
Правильная формулировка: **валидный GNS data-пакет стоит игровому треду
в 2–4 раза дороже мусорного**, и деградация возникает, когда темп входящих
пакетов превышает скорость, с которой тик успевает их разобрать.

### 16.3 Стоимость одного пакета (CPU процесса сервера, мкс/пакет)

| Вариант пакета | мкс/пакет | соединений | комментарий |
|---|---|---|---|
| мусор 64 Б на 7778 | **10.6** | 0 | базовая цена приёма и отброса |
| GNS data, 1 unreliable-кадр, payload 6/64/512/1400 Б | 20–24 | +1 на пакет | **размер payload не влияет** |
| GNS data, 1 reliable-кадр (0x40) | 20.1 | +2 252 | надёжный путь |
| GNS data, 10 unreliable-кадров | 29.1 | +1 на пакет | |
| **GNS data, 10 reliable-кадров (0x40)** | **39.8** | +5 | **самый дорогой вариант** |
| GNS ack-кадр (0x90) | 28.3 | 0 | сервер обновляет счётчики |
| GNS data с флагом blob (0x81) | 22.6 | 0 | |

Отсюда — **доработка вектора**: самый выгодный для атакующего пакет — это
10 reliable-кадров в одном датаграмме (≈40 мкс обработки против 10.6 мкс у
мусора, т.е. **в 3.8 раза дороже**). Размер payload значения не имеет.

### 16.4 Порог деградации

| Темп | Транспорт | Результат |
|---|---|---|
| ~8 000 pps | GNS data | эффекта нет (TPS мин 20.7) |
| ~25 000 pps | GNS data | **TPS 21.7 → 2.5** (падение в 10 раз) |
| ~43 000 pps | мусор | эффекта нет (TPS мин 21.0) |
| ~242 000 pps | мусор (12 источников) | эффект есть (прежнее измерение) |

⇒ Вектор с поддельной GNS-сессией примерно **в 10 раз дешевле** мусорного
флуда по требуемому темпу, а с reliable-кадрами выигрыш ещё выше (стоимость
пакета ×3.8).

### 16.5 Отрицательный результат: «постоянные» соединения не подтвердились

Гипотеза: если завершить UE4-хендшейк, соединение останется жить и стоимость
перейдёт на сервер (память + итерации по соединениям в тике) — тогда атакующий
может перестать слать пакеты.

Что сделано: подделана GNS-сессия, затем в неё отправлены **копии data-пакетов
настоящего клиента** (перехват `gns_relay_capture.jsonl`) с подменой
`to_connection_id` на выданный сервером.

* Сервер **начал отвечать** непрерывным потоком GNS-датапакетов (246 пакетов /
  4.9 КБ за 30 с) — рукопожатие на стороне сервера продвинулось;
* 200 таких сессий дали **+42 МБ** памяти (≈210 КБ на соединение);
* **но** UE4-соединения не удерживаются: `liveConnections` возвращается к 2,
  память освобождается через ~10 с. Живут только GNS-соединения (уровня
  транспорта), UE4-соединения закрываются, потому что cookie не проходит
  проверку (он выдан реальному клиенту).

**Вывод:** «постоянный» DoS не подтверждается — плата за соединения небольшая
(210 КБ) и они недолговечны. Поэтому основная форма вектора — **волна**
пакетов: атакующий держит темп ~25 000 pps, сервер проваливается в 10 раз,
а после остановки восстанавливается за 15–20 с.

### 16.6 Итоговый рейтинг с поправкой

| # | Вектор | Мощность (по TPS) | Цена | Примечание |
|---|---|---|---|---|
| 1 | **GNS-сессия + data-пакеты (10 reliable-кадров)** | **88–98 %** (TPS 21.7 → 2.5) | ~25 000 pps (≈20–25 тыс. пакетов = 100 тыс. до обвала) | эффект даёт **транспорт**, не создание соединений |
| 2 | мусорный флуд 7778 | 0 % на 43 000 pps | ~242 000 pps | в 10 раз дороже |
| 3 | GNS ChallengeRequest / ConnectRequest / A2S-флуд | 0–2 % | — | состояния не создают / отражения дают x15 |
| 4 | «фейковые игроки» (слоты) | 0 % | 70 аккаунтов | слоты не занимаются (§12) |

**Ограничения применимости (честно):**
* деградирует **игровой тред** (игроки, их пакеты), но **не доступность сервера**:
  A2S-порт обслуживается отдельным потоком и продолжает отвечать (локально
  RTT не изменился: 47–63 мс). На внешнем VPS эффект выглядит сильнее, потому
  что там страдает весь бокс (50 % потерь на query-порту);
* эффект транзиентный: 15–20 с после остановки флуда;
* «1 пакет = 1 `UNetConnection» — факт, но не механизм: стоимость в обработке
  пакета, а соединения живут ~10 с и стоят ~210 КБ.

### 16.8 Решающий контроль: тип data-кадра (исправление к §16.2)

§16.2 сравнивал «GNS + мусор» и «GNS + UE4-хендшейк» и получил одинаковую
деградацию. Это **не доказывало**, что виноват транспорт: обе разновидности
создают `UNetConnection` (счётчик растёт и при мусорном payload — соединение
создаётся до проверки содержимого). Различающий контроль — **тип SNP-кадра**
внутри data-пакета: unreliable-кадр (0x37) доходит до UE4 как stateless-connect
и создаёт соединение; reliable (0x40) и ack (0x90) обрабатываются только
транспортным слоем и соединений не создают.

Локальный стенд, по 120 000 пакетов на вариант, 22–27 тыс. pps:

| Вариант data-пакета | **TPS мин** | Соединений создано | Эффект |
|---|---|---|---|
| `unreliable` (0x37, 1 кадр) | **2.6** | +120 000 | **деградация** |
| `unreliable-x10` (10 кадров 0x37) | **2.7** | +120 000 | **деградация** |
| `blob` (0x81 + inline protobuf) | **2.7** | +120 000 | **деградация** |
| `mixed` (0x37 + 0x40 + 0x90) | **2.7** | +120 000 | **деградация** |
| `reliable` (0x40, 1 кадр) | **21.1** | 0 | **нет эффекта** |
| `reliable-x10` (10 кадров 0x40) | **21.1** | 0 | **нет эффекта** |
| `ack` (0x90) | **21.1** | 0 | **нет эффекта** |

**Итог: деградацию даёт именно создание `UNetConnection`, а не обработка
транспорта.** Формулировка «1 пакет = 1 `UNetConnection`» в §14 подтверждена
контролируемым экспериментом. Практические следствия:

* самый дешёвый для атакующего — **обычный unreliable-кадр** (1 кадр, 18 байт
  пакета): добавление 9 дополнительных кадров в пакет ничего не даёт
  (соединение всё равно одно, TPS мин 2.6 против 2.7);
* reliable/ack-кадры для DoS бесполезны: они не создают соединений и не
  деградируют сервер (их можно использовать только как «тихий» трафик);
* стоимость обработки (CPU): unreliable 20–25 мкс/пакет, reliable 20,
  reliable×10 40, ack 28 — то есть **самый дорогой по CPU вариант (reliable×10)
  наименее эффективен**: дорогая обработка без создания соединений.

### 16.9 Проверка на внешнем сервере: ранжирование вариантов невозможно

Тот же прогон на внешнем стенде `23.109.45.13:25714` (по 150–200 тыс. пакетов
на вариант, измеряется по потерям на query-порту):

| Вариант | Потери на query-порту | RTT макс |
|---|---|---|
| unreliable | 19.0 % / 27.8 % | 170 / 143 мс |
| unreliable-x10 | 15.0 % | 178 мс |
| blob | 15.8 % | 174 мс |
| mixed | 15.8 % | 385 мс |
| reliable-x10 (контроль) | 31.2 % / 26.3 % | 404 / 168 мс |

**Контрольный вариант (`reliable-x10`, который локально не создаёт соединений и
не деградирует) показывает столько же потерь, сколько эффективные** ⇒
на удалённом сервере сигнал полностью забит шумом WAN-канала, и ранжировать
варианты по нему нельзя. Ранжирование даёт только локальное измерение по FPS.

Дополнительно: локальный стенд при всех прогонах по внешнему серверу остался
незатронутым (TPS 21.1–21.7, Δ `packetsReceived` = 0) — контроль, что весь
трафик уходил на удалённый хост.

### 16.10 Итоговая формулировка вектора (после всех контролей)

> **Один data-пакет GNS с unreliable-кадром (0x37) = один `UNetConnection`,
> созданный сервером.** Именно создание соединения (в каждом тике: аллокация,
> инициализация, регистрация в списке NetDriver, разбор stateless-connect,
> уничтожение) роняет FPS игрового треда: **21.7 → 2.5** при ~25 000 pps,
> порог обвала — ~100 000 пакетов, восстановление 15–20 с. Аутентификация на
> транспорте отсутствует (обычный `ConnectRequest` без cert принимается), поэтому
> атака не требует ни Steam-аккаунта, ни криптографии.
> Защита: сетевая (закрыть/ограничить UDP 7778) — прикладной клапан на
> `NotifyAcceptingConnection` неэффективен (отклонённые соединения всё равно
> стоят серверу аллокации и разбора).

### 16.11 «Только для локалки?» — порог деградации на разных серверах

Наблюдение пользователя: на внешнем сервере эффекта не видно. Проверено
ступенчатым тестом (`ark_lab_remote_threshold.py`) — по 100…500 тыс. пакетов
на внешнем сервере `23.109.45.13:25714` (вариант `unreliable`, ~19–20 тыс. pps):

| Пакетов | pps | Секунд | Потери на query-порту (во время флуда) | Потери (база, без флуда) | RTT макс |
|---|---|---|---|---|---|
| 100 000 | 19 436 | 5.1 | **0.0 %** | 0.0 % | 312 мс |
| 200 000 | 20 384 | 9.8 | **0.0 %** | 0.0 % | 96 мс |
| 300 000 | 18 832 | 15.9 | **0.0 %** | 0.0 % | 96 мс |
| 500 000 | 19 708 | 25.4 | **3.4 %** | 0.0 % | 97 мс |

**Ответ: эффект не «только для локалки», но его величина определяется ресурсами
сервера.** Локальный стенд обрушивается на ~80–100 тыс. пакетов
(TPS 21.7 → 2.5), внешний VPS — только на ~500 тыс. (и пока лишь 3.4 % потерь
на query-порту). Разница в 5–6 раз.

**Почему локальный стенд так чувствителен (методологические оговорки):**

| Фактор | Влияние |
|---|---|
| **Сервер зажат на 4 ядрах** (маска `0xF00000`, ядра 20–23) на хосте с 24 ядрами | запас CPU у сервера минимален; любой дефицит CPU сразу виден в тике |
| **На том же хосте работает Server1** (тот же каталог менеджера, порт 7777) + Steam-клиент + инструментарий | CPU и сеть хоста делятся между двумя ARK-серверами и клиентом |
| **Пакеты идут по локальному пути** (в пределах одного хоста) | тот же темп на loopback/LAN-драйвере даёт куда более высокую нагрузку на прерывания/softirq, чем на реальной сети |
| **На локалном сервере стоит диагностический плагин NetGuard** (хуки на `ReceivedRawPacket` и `NotifyAcceptingConnection` + файл захвата) | добавляет работу в игровом треде; сам захват ограничен 4000 пакетов, хуки — единицы мкс на пакет, то есть вклад мал, но не нулевой |
| **Атакующий тоже на этом хосте** | его CPU конкурирует с теми же ядрами; контрольный тест (мусор) показал, что это не причина: при том же темпе мусор эффекта не даёт |

**Как это меняет оценку вектора (честно):**

* механизм (создание `UNetConnection` игровым тредом) — одинаков на всех стендах,
  это подтверждается и тем, что внешний сервер при 500 тыс. пакетов всё-таки
  начинает терять ответы;
* **практическая цена атаки на типовом внешнем сервере выше, чем показывает
  локальный стенд**: 80–100 тыс. пакетов (~3–5 МБ) на внешнем VPS эффекта не
  дают, нужно ~500 тыс. (~20 МБ) и выше;
* «деградация FPS в 10 раз» — это характеристика **местного стенда**, а не
  универсальная величина; в рейтинге это отмечено;
* наблюдаемый снаружи эффект (потери на query-порту) требует, чтобы пострадал
  весь бокс, а не только игровой тред — на VPS с запасом CPU этого не происходит,
  и это правильное поведение: игроки страдают от просадки FPS, но сервер остаётся
  доступным.

**Что стоит сделать дальше (следующий шаг по вектору):** измерить порог на
внешнем сервере при **нескольких источниках** одновременно (суммарный темп
выше, чем может выдать один поток Python: с одного источника удаётся ~20 тыс. pps)
и проверить, восстанавливается ли внешний сервер так же быстро, как локальный.

> Примечание: на момент этих измерений локальный стенд Server2 (с плагином
> NetGuard) остановлен, поэтому локальные замеры для продолжения работы нужно
> будет возобновить после его перезапуска.

### 16.12 Можно ли эффективнее и дешевле? — разбор рычагов

Проверены три гипотезы «дешёвой» атаки; все три дали чёткий ответ.

**Гипотеза A: несколько UE4-соединений в одном сетевом пакете** (положить в
один data-пакет N полных UE4-пакетов «stateless connect», каждый со своим
номером последовательности, каждый в своём SNP-кадре).

| Вариант | Сетевых пакетов | Соединений создано | Соединений на пакет |
|---|---|---|---|
| `ue4-62b` (один connect в пакете) | 20 000 | 20 000 | 1.00 |
| `ue4-multi4` (4 connect'а в пакете) | 20 000 | 20 000 | 1.00 |
| `ue4-multi10` | 20 000 | 20 000 | 1.00 |
| `ue4-multi20` | 20 000 | 20 000 | 1.00 |

**Опровергнуто.** UE4-слой обрабатывает датаграмму как один поток: первый
stateless-connect «съедает» пакет, остальные уходят в него же. Потолок
«1 сетевой пакет = 1 `UNetConnection`» уже достигнут, обойти его нельзя.

**Гипотеза B: дешёвая за счёт размера пакета** — размер payload не влияет на
стоимость (6 Б ≈ 64 Б ≈ 512 Б ≈ 1400 Б ≈ 20–24 мкс/пакет по CPU процесса).
Значит, «толстый» пакет не даёт выигрыша: цена атаки измеряется **числом
пакетов**, а не байтами. Трафик 500 тыс. пакетов = 9 МБ полезной нагрузки
(~30 МБ на проводе) — по полосе атака неинтересна.

**Гипотеза C: постоянные соединения** (завершить stateless-connect, чтобы
соединение жило до таймаута 300 с и сервер нёс его в каждом тике). Проверено
двумя способами: копия data-пакетов настоящего клиента (100 сессий) и
чтение ответов сервера (иначе буфер приёмки переполняется и сервер рвёт
сессию сам). Результат: `liveConnections` 0–1, память не накапливается,
соединения живут секунды. Причина — cookie stateless-connect выдан реальному
клиенту и к нашей сессии не привязан; чтобы сделать соединение живым, нужно
разобрать обмен UE4-handshake (challenge сервера → cookie) и подделать его —
это отдельная задача, и даже при её решении выигрыш ограничен памятью
(≈210 КБ на соединение) и накладными расходами NetDriver в тике, а не
самим обрушением FPS.

**Итог по эффективности: вектор уже на практическом оптимуме по «урон на
пакет»** (1 пакет = 1 соединение, цена фиксирована ~17 мкс CPU сервера).
Остаются два реальных рычага:

| Рычаг | Что даёт | Цена |
|---|---|---|
| **Темп (несколько источников)** | обвал начинается, когда входящий темп выше скорости разбора тика (~25 тыс. pps на локальном стенде); 4 параллельных отправителя дают ~80–100 тыс. pps | ~1.5 МБ/с трафика, 4–10 с работы |
| **Другой класс вектора** | `ServerCheat` RPC (вектор №1) — 1 пакет = выполнение серверной команды (не DoS, а повышение привилегий) | 1 пакет |
| **Отражение (A2S, x15)** | трафик к third parties от имени сервера | 1 пакет → 446 Б |

То есть «более дешёвого» варианта **этого** вектора нет; экономить можно
либо на объёме (за счёт роста темпа), либо выбирать другой класс воздействия
(команда, а не отказ в обслуживании).
