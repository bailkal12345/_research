# Распараллеливание GameThread — ARK: Survival Evolved v361 (ShooterGameServer.exe)

Анализ выполнен 2026-10-16/17 на машине: Xeon E5-2697 v2, **24 логических ядра**, 64 ГБ RAM.

Все утверждения проверены одним из трёх способов: дизассемблированием
`ShooterGameServer.exe` (дамп v361 в Ghidra), исходниками UE4.5 в
`C:\Dev\UnrealEngine-4.5`, либо измерением на живом сервере
`C:\asmdata\Servers\Server1`.

---

## 0. Главный вывод

1. Dedicated server ARK SE v361 физически однопоточен: **GameThread 0.93–0.97 ядра из 24**,
   остальные 23 ядра и все 30 потоков процесса простаивают.
2. Причина найдена и **доказана в машинном коде**: `FTickTaskSequencer::SingleThreadedMode()`
   возвращает `true` на dedicated server, компилятор свернул это в константу,
   и `bAllowConcurrentTicks` записан как `false`. Все тик-функции акторов и компонентов
   публикуются как GameThread-задачи. Второй замок: `FTickFunction::bRunOnAnyThread`
   во всём UE4.5 **никогда не выставляется** — асинхронные тики мертвы в стоке.
3. Профиль показывает, что bottleneck — **не тики акторов**, а collision/overlap-запросы,
   разрешение имён/UObject и аллокации. Это принципиально меняет план работ.

## 2. Почему всё крутится на одном потоке

### 2.1 Исходники UE4.5

`Engine/Source/Runtime/Engine/Private/TickTaskManager.cpp:93`

```cpp
FORCEINLINE static bool SingleThreadedMode()
{
    if (IsRunningDedicatedServer() || FPlatformMisc::NumberOfCores() < 3)
        return true;
    return false;
}
```

Это единственный переключатель всего диспетчера тиков:

* `StartFrame():` при `SingleThreadedMode()` → `bAllowConcurrentTicks = false`,
  ветка с CVar `AllowAsyncComponentTicks` не выполняется вовсе;
* `StartTickTask():` `UseContext.Thread = ENamedThreads::GameThread` — задачи тиков
  публикуются как GameThread;
* `RunTickGroup():` `if (bBlockTillComplete || SingleThreadedMode())` — группы
  ждутся инлайн.

### 2.2 Подтверждено дизассемблированием v361

`FTickTaskSequencer::StartFrame`, RVA `0x270B500` (в дампе переименована, тег `tickpath`):

```c
iVar4 = TAutoConsoleVariable<int>::GetValueOnGameThread(&CVarLogTicks);
this->bLogTicks = iVar4 != 0;
this->bAllowConcurrentTicks = false;        // ← литерал, проверок нет
```

Ни `IsRunningDedicatedServer()`, ни чтения `CVarAllowAsyncComponentTicks` в коде нет:
компилятор вычислил `SingleThreadedMode()` на этапе сборки серверного бинарника.
Строка `AllowAsyncComponentTicks` в бинарнике есть (регистрация CVar), но её значение
не читается никогда. `FTickTaskManager::StartFrame` (RVA `0x270DB60`) содержит
`(this->Context).Thread = GameThread;`.

### 2.3 Второй замок: `bRunOnAnyThread` мёртв

`TickTaskManager.cpp:117` — единственное чтение флага:

```cpp
if (TickFunction->bRunOnAnyThread && bAllowConcurrentTicks && bIsOriginalTickGroup)
    UseContext.Thread = ENamedThreads::AnyThread;
```

Прогон по всему `Engine\Source` даёт ровно три вхождения `bRunOnAnyThread`:
объявление UPROPERTY, инициализация `false` в конструкторе (строка 951) и это чтение.
Ни `UActorComponent::RegisterComponentTickFunctions`, ни
`UActorComponent::SetupActorComponentTickFunction` (строка 477) флаг не выставляют;
поле `bAllowConcurrentTick` в них не используется.

**Следствие:** даже после снятия п. 2.2 тик уйдёт на воркер только для тех
тик-функций, у которых флаг выставлен вручную.

## 5. Что не удалось и почему

* **`dbghelp` не читает этот PDB**: `SymEnumSymbols`/`SymFromAddr` возвращают 0 символов
  при валидной RSDS-записи. Рабочий путь — DIA (`msdia140.dll`), как у ArkApi.
* **Хук `FEngineLoop.Tick` роняет сервер.** Адрес резолвится верно: DIA отдаёт
  `addressOffset = RVA − 0x1000`, ArkApi складывает `imageBase + BaseOfCode + offset`
  и получает правильный VA. После установки хука GameThread встаёт в
  `ReportCrash → ReportCrashUsingCrashReportClient → FMessageDialog::Open` —
  это модальное окно краш-репортера, процесс жив, но не тикает.
* **Второй хук на `UWorld.Tick` тоже роняет сервер**: на этой функции уже висит хук
  самого ArkApi (`CheckOnTickCallbacks`), цепочка детектов ломается.
* **Хуки на `AShooterGameMode.Tick` / `UWorld.TickNetClient` нестабильны**: в одних
  прогонах держатся, в других роняют сервер. Рабочие и проверенные:
  `UWorld.RunTickGroup`, `FTickTaskManager.StartFrame`, `FTickTaskManager.EndFrame`,
  `UNetDriver.TickDispatch`, `Global.CollectGarbage`.
* **Синтетическая нагрузка не создаётся**: и `UShooterCheatManager::SpawnDino`,
  и `UWorld::SpawnActor` по классу динозавра роняют сервер тем же краш-репортером.
  Поэтому профиль снят на естественной нагрузке (без игроков).
* **Фазовые таймеры не получены**: рабочие хуки ставились, но прогон успевал упасть
  на `AShooterGameMode.Tick` до старта второй фазы сэмплирования. Профиль по RIP
  получен и он информативнее.

## 6. План распараллеливания

### Шаг 1. Снять запрет на асинхронные тики (патч 1 байт)

`FTickTaskSequencer::StartFrame`, RVA `0x270B500`: инструкция, записывающая
`this->bAllowConcurrentTicks = false`, меняется на запись `true`.

CVar `AllowAsyncComponentTicks` бесполезен — компилятор убрал его чтение.
Ожидаемый эффект: `StartTickTask` начнёт выбирать `ENamedThreads::AnyThread`
для всех тик-функций с `bRunOnAnyThread`.

### Шаг 2. Разметить безопасные тик-функции

Обойти `FTickTaskLevel::AllEnabledTickFunctions`, для каждой тик-функции проверить:
нет prerequisites, класс компонента в белом списке (без доступа к UObject-реестру,
без net/GC), и проставить `bRunOnAnyThread`. Ожидаемая доля — текущие ~5.5%
(тики сущностей) плюс часть компонентов.

Ограничения, которые нельзя игнорировать:
* любая тик-функция с `AddPrerequisite` останется в GameThread — задача ждёт
  предшественника, и это не параллелится;
* порядок относительно `TG_StartPhysics/TG_EndPhysics` сохраняется
  (у каждой группы свой барьер);
* компоненты, пишущие в `GUObjectArray` или трогающие `UWorld`, исключать.

### Шаг 3. Главный выигрыш по профилю: collision/overlap ≈29%

Это не тики, это запросы — значит дешевле не «раскидать», а снять цену:

1. `TArray<FOverlapInfo>::AddUniqueImpl` — линейный поиск на каждый элемент,
   то есть O(n²) на результат запроса. Замена на `TInlineAllocator` + сортировку
   или на битовое множество даёт самостоятельный выигрыш без параллелизации.
2. Пакетирование: один `GeomOverlapMulti` на набор акторов вместо N запросов.
   Физический сценарий трогать нельзя — он не потокобезопасен, но группировка
   запросов безопасна.
3. Кэш результатов между тиками для статичных геометрий (мир ARK статичен).

### Шаг 4. Разрешение имён и объектов ≈7%

`TSet<TPair<FName,FFoliageMeshInfo*>>::FindId` (1.7%) и `FName::FindOrAddNameEntry`
(1.8%) вызываются каждый кадр с одними и теми же именами. Нужен кэш
`FName → указатель`, живущий дольше одного кадра; то же для
`FPostConstructInitializeProperties::InitProperties` и `StaticFindObject`.

### Шаг 5. Память ≈6.5%

`FMallocBinned` (2.2%) плюс memcpy/memset в MSVCR120 (4.3%) — следствие
описанного выше: запросы постоянно создают и копируют массивы. После шага 3
это уменьшится само; отдельно имеет смысл поднять лимиты батчевой аллокации.

### Шаг 6. Репликация и GC

`UActorChannel::ReplicateActor` обязан идти в фиксированном порядке на GameThread,
но сериализацию свойств можно готовить на воркерах между тиками.
GC (`CollectGarbage`) — кандидат на инкрементальный перенос на воркер; на сервере
уже стоит плагин NoGC.

### Чего достичь нельзя

«Полностью» распараллелить GameThread — переносом тика мира на несколько потоков —
нельзя без переписывания движка: `UWorld::Tick` имеет глобальные зависимости
порядка (создание и учёт UObject, состояние уровней, порядок репликации,
барьеры physics-групп). Реалистичная цель: снять с GameThread основную массу
работы — а профиль показывает, что это collision, разрешение имён и память,
а вовсе не тики акторов.

## 6а. Что реально сделано и измерено

Все правки реализованы в плагине `TickProf` и включаются на живом сервере
командами RCON, с возможностью отката.

Смещения структур получены из PDB утилитой `fieldcheck.exe` (DIA):

| Что | Смещение |
|---|---|
| `FTickFunction` битфилд | dword @ +12, `bRunOnAnyThread` = бит 4 (0x10) |
| `FTickFunction::Prerequisites` | TArray @ +40 |
| `FTickFunction::TickGroup` | +8 |
| `FTickTaskSequencer::bAllowConcurrentTicks` | +560 |
| `AActor::PrimaryActorTick` | +40 |
| `UActorComponent::PrimaryComponentTick` | +48 |
| `ULevelBase::Actors` | TArray @ +136 |
| `UPrimitiveComponent::OverlappingComponents` | TArray @ +1312 |
| `UPrimitiveComponent::bGenerateOverlapEvents` | бит 10 в dword @ +500 |
| `UObjectBase::Class` | +16 |

### Инструмент 1: патч `bAllowConcurrentTicks`

Инструкция `C6 86 30 02 00 00 00` (`MOV byte ptr [RSI+0x230], 0`) в
`FTickTaskSequencer::StartFrame` (RVA `0x270B534`); непосредственный операнд —
байт по RVA `0x270B53A`. Перед патчем проверяются все 7 байт опкода (`C6 86 disp32 imm8`) — при
любом несовпадении патч отменяется (в ходе работы проверка однажды спасла
сервер от патча по неверному смещению).

Команды: `TickProf.fix concurrent 1|0`, проверка — `TickProf.verify`.

### Инструмент 2: разметка тик-функций

Обход акторов всех 104 уровней (`ULevelBase::Actors`) и всех компонентов
одним вызовом движка (`GetObjectsOfClass(UActorComponent::StaticClass)`),
далее прямое чтение/запись битов. Режимы: 0 снять, 1 все, 2 компоненты
`TG_DuringPhysics` без prerequisites, 3 `TG_PrePhysics`, 4 только тики
акторов, 5 все без prerequisites. Есть вариант с белым списком классов из файла.

Перепись показала: **52 780 тик-функций из 276 292**, из них 5 281 с
prerequisites; тикущих актеров 424, тикущих компонентов 599.

### Инструмент 3: кэш Kismet-канвасов

2.5% профиля уходило в `TSet<FName,FFoliageMeshInfo*>::FindId`, которую зовут
`DoGetCanvasByName` / `GetCanvasByName` / `FindFunctionByName` — поиск канвасов
графа Kismet. На dedicated server канвасы не рисуются. Хук на
`Global.DoGetCanvasByName` (`UCanvas* __cdecl DoGetCanvasByName(FName)`) с
таблицей на 1024 слота, отрицательные ответы тоже кэшируются.

### Инструмент 4: обрезка перегруженных пересечений

`UPrimitiveComponent::BeginComponentOverlap` для каждого события делает
линейный `IsOverlappingComponent` и линейный `AddUnique` в
`OverlappingComponents` второго компонента — то есть O(n²) на компонент.
Команда `TickProf.overlaptrim <порог>` находит компоненты с числом записей выше
порога, очищает массив и снимает `bGenerateOverlapEvents`.

### Результаты (внешний CPU потока GameThread, окно 40 с)

| Шаг | CPU, s/s | тиков/с | время кадра |
|---|---|---|---|
| BASELINE | 0.746 | 14.2 | 70.7 мс |
| + кэш канвасов | 0.605 | 28.3 | 35.3 мс |
| + обрезка пересечений (порог 32) | 0.402 | 29.7 | 33.7 мс |
| + обрезка пересечений (порог 8) | 0.254 | 29.8 | 33.6 мс |

Итого по двум правкам: **GameThread −66% CPU, пропускная способность ×2.1**
(14.2 → 29.8 тиков/с). Обрезка сняла 495 051 записей пересечений с 24 369
компонентов; обрезка по порогу 32 — 260 278 записей с 787 компонентов.

Число тиков в секунду упёрлось в 29.8 — это штатный предел
`NetServerMaxTickRate`, то есть после этих правок GameThread перестал быть
узким местом, и дальнейшая его разгрузка без роста тикрейта бессмысленна.

алгоритмам ARK-игрового кода, а адреса и смещения брались из PDB сервера.

Индекс имён построен (`dump_index.json`), тела функций извлекаются по имени.

### Что дал разбор дампа

**1. Второй сайт O(n²).** `UVictoryCore::ServerOctreeOverlapActorsBitMask`
(серверный помощник ИИ «кого я могу атаковать») внутри цикла по результатам
октри-поиска вызывает `AddUnique` **дважды на каждый результат** — в список
динозавров и в список контейнеров структур. Тот же антипаттерн, что и в
`OverlappingComponents`, но в ARK-специфичном коде.

**2. Первопричина 3.3% профиля в поиске по имени.** `UObject::ExecuteUbergraph`
— диспетчер blueprint-графов — вызывает
`UClass::FindFunctionByName(this->Class, (FName)0xe0, InIncludeSuper)`
с **константным** FName на каждом тике blueprint-объекта. Поиск обходит цепочку
классов и интерфейсы, делая `TSet::FindId` на каждом уровне. Результат для пары
(класс, имя) неизменен — идеальный кандидат в кэш.

**3. Систематический поиск** всех функций с ≥2 вызовами `AddUniqueImpl` дал
38 функций; все прочие — `GetLifetimeReplicatedProps` (однократно при регистрации
класса) и `InitRHI` (рендер, на сервере не исполняется). Новых горячих
O(n²)-мест в дампе нет.

## 8. Итоговая оценка целесообразности

**Применять (безопасно, подтверждено замерами):**

| Правка | Команда | Почему безопасна |
|---|---|---|
| Кэш `FindFunctionByName` | `TickProf.fncache 1` | набор функций класса неизменен; отрицательные ответы кэшируются |
| Кэш `IsChildOf` | `TickProf.iscache 1` | иерархия классов на сервере не меняется |
| Кэш `DoGetCanvasByName` | `TickProf.cachename 1` | набор канвасов за сессию не меняется |
| Обрезка пересечений, порог 2 | `TickProf.overlaptrim 2` | трогаются только компоненты с уже раздутым списком пересечений |
| Асинхронная физика | `p.bTickPhysicsAsync 1` | штатный CVar движка; проверено отдельно — сервер не вешает |

Готовый сценарий: `python C:\Dev\_research\apply_recommended.py`
(откат — `apply_recommended.py --revert`).

**Не применять:**

| Правка | Почему |
|---|---|
| Патч `bAllowConcurrentTicks` + `bRunOnAnyThread` | ускоряет параллелизм, но замедляет сервер: 33.4 → 42–46 мс/кадр |
| Полное отключение overlap-событий | ломает геймплей (ловушки, восприятие ИИ, триггеры) ради ~0.07 s/s |

**Общий вывод.** Полностью распараллелить GameThread переносом тиков на воркеры
в этой сборке нельзя: движок сознательно отключил этот путь, и наша попытка
включить его его же подтвердила. Реальный результат даёт **не параллелизм, а
снятие лишней работы**: четыре кэша плюс обрезка пересечений снижают CPU
GameThread на 79% и поднимают пропускную способность с 15.5 до 29.9 тиков/с —
доводят сервер до его штатного предела `NetServerMaxTickRate`. После этого
GameThread простаивает 92.6% времени, и дальнейшее снижение CPU возможно
только ценой отключения игровой логики.

Отдельно про зависание: в одном прогоне сервер перестал отвечать после
`p.bTickPhysicsAsync 1`. Повторная изолированная проверка (контроль 30 с,
с асинхронной физикой 60 с, возврат 30 с) зависания не воспроизвела — виновником
было сочетание с полным отключением overlap-событий на 139 745 компонентах.
Вывод: `p.bTickPhysicsAsync` сам по себе безопасен, но сочетать его с
`overlapall` нельзя.

## 9. Снятие лимита тиков: динамика

Штатное ограничение — `UNetDriver::NetServerMaxTickRate` (**int32**, смещение 72 по PDB;
декомпил: `MOV EDX,[RAX+0x48]` → целочисленный `CMP/CMOVL` → `CVTDQ2PS`).
Cvar `net.MaxNetTickRate` в этой сборке **отсутствует** (строки в бинаре нет), а
`UEngine::GetMaxTickRate` возвращает 0 и занимается только `t.MaxFPS` и сном при
 hitch — ограничителем не является.

Команда `TickProf.maxfps <N>` пишет поле напрямую и переустанавливает его раз в
5 с (драйвер может переинициализироваться). `TickProf.maxfps 0` возвращает штатное
поведение.

Замер: окно 30 с, внешний CPU потока GameThread, сервер в установившемся режиме.

| Лимит | тиков/с | CPU, s/s | мс CPU на тик |
|---|---|---|---|
| 30 (штатно) | 15.5* | 0.961 | 62.00 |
| 60 | 53.8 | 0.977 | 18.14 |
| 120 | 53.8 | 0.938 | 17.41 |
| 300 | 82.9 | 0.898 | 10.83 |
| 1000 | 110.2 | 0.672 | 6.10 |
| **200000** | **114.1** | **0.531** | **4.66** |

\* первое окно попало на фазу стриминга мира, поэтому время на тик завышено.

**Что показывает динамика.** Потолок — не 30, а **114 тиков/с**: это и есть реальная
пропускная способность GameThread в установившемся режиме, то есть **4.66 мс
работы на один тик мира**. Сервер на штатных настройках использует 0.53 ядра из 24 —
это 2% машины.

Главный практический вывод: после снятия потолка метрика «тиков/с» перестаёт быть
бесполезной и становится прямой мерой эффекта любой оптимизации. На лимите 30 все
измерения упираются в потолок, и правки не видны; на лимите 200000 каждая миллисекунда
на тик превращается в прирост пропускной способности. Именно поэтому все дальнейшие
сравнения проведены на снятом лимите.

Побочный эффект для диагностики: поднятый лимит тиков полезен сам по себе как
стресс-тест — на лимите 200000 вскрываются вещи, невидимые при 30.

| без оптимизаций | 117.7 | 0.328 | 2.79 | — |

Фазовые таймеры (окно 40 с, 4465 кадров, 111.6 тиков/с, 8.96 мс на кадр):

Итого измеренными фазами занято **21.7 с из 40 с**, то есть 54% кадра.
Оставшиеся ~46% — вне наших хуков: основной цикл движка, сетевой код,
ожидание воркеров и сон таймерного ограничителя.

**Вывод, меняющий стратегию.** Потолок в ~117 тиков/с — не CPU: на него

чтобы поднять пропускную способность, нужно сокращать **не CPU, а время
ожидания**, а оно задано гранулярностью сна и барьерами задачного графа.

При этом на штатном лимите 30 тиков/с все оптимизации остаются осмысленными:
там они снижают нагрузку на 79% и полностью убирают GameThread из узких мест
профилирования. Два вывода не противоречат друг другу — они отвечают на разные
вопросы: «сколько CPU нужно» и «какая скорость достижима».

### Отсечение тиков по расстоянию — роняет сервер

`TickProf.cull 15000` (пропуск тика акторов дальше 15 км от игрока) через
несколько секунд приводит к тому, что GameThread уходит в 1.7 s/s, а RCON
перестаёт отвечать. Откатить командой уже нельзя — нужен перезапуск сервера
(игрок при этом отключается).

Причина понятна: пропуск `AActor::TickActor` ломает инварианты движка. У
актора тик — не только «поведение», но и обслуживание состояния: отложенные
операции, таймеры, обновление состояния репликации. Акоторы, чей тик пропущен,
остаются видимыми для системы тиков и сетевых проверок, но перестают
обслуживаться — и накапливается рассогласование, которое валит GameThread.

**Решение: команда заблокирована.** Теперь `TickProf.cull` требует явного
аргумента `force` и по умолчанию отказывает, выводя предупреждение.
Применять нельзя.

### Что добавлено по итогам

| Команда | Что делает | Статус |
|---|---|---|
| `TickProf.nochart 1` | отключает `UEngine::TickFPSChart` — ведение графиков FPS на сервере | безопасно |
| `TickProf.cull` | отсечение тиков по расстоянию | **заблокировано, роняет сервер** |
| `TickProf.tickoff` | выключение тика у компонентов по классу | работает, но на живом сервере не применялся |

`TickProf.nochart` снимает чисто серверную работу (0.47% профиля): на
dedicated server графики кадров смотреть некому, а `TickFPSChart` считает их
каждый кадр.

### Опасные операции, найденные попутно

| Операция | Последствие |
|---|---|
| `plugins.unload TickProf` при активных фазовых хуках | сервер зависает (воспроизведено дважды) |

| выгрузка плагина при подключённом игроке | не проверялось, рискованно |


### Финальный прогон только с безопасными правками

Окна 30 с, тикрейт 30, сервер с подключённым игроком. Измерения шли вскоре
после старта мира, поэтому абсолютные значения завышены (стриминг), но
последовательные приращения внутри прогона сопоставимы.

Профиль после всех правок: первые места — `APrimalCharacter` (5.8%),

## 11. Раунд П1: сколько задач реально ставится в очередь

### Сводка чисел по тик-функциям (одна цепочка)

| Уровень | Что означает | Значение |
|---|---|---|
| 1 | акторов и компонентов, у которых **есть** тик-функция (перепись по объектам) | 52 780 |
| 2 | записей в `AllEnabledTickFunctions` — то, что реально обходит менеджер | **3 510** |
| 3 | задач, реально поставленных в очередь за кадр (счётчик `QueueTickFunction`) | **223** |

Переход 52 780 → 3 510 идёт при регистрации тика, 3 510 → 223 — при фильтрах
(fast-path, prerequisites, отключённые). Ни одна из этих величин не объясняет
2.7 мс `StartFrame`: 3 510 × 72 нс = 0.25 мс, 223 × 5.4 мкс — абсурдно много.


### Что предполагалось

Гипотеза брифа: `FTickTaskManager::StartFrame` (~2.7–3.8 мс на кадр) — это учёт
~52 780 зарегистрированных тик-функций, из которых большинство принадлежит
стасисованным динозаврам; они ставятся в очередь каждый кадр и сразу
выходят. Отсюда оценка 72 нс на задачу — правдоподобная цена создания
task-узла. Отсюда же прогноз: убрать мёртвые функции → StartFrame падает
до ~0.1 мс, потолок растёт со 117 до 250–400 тиков/с.

### Что измерено

Счётчик вызовов `FTickFunction::QueueTickFunction` за окно 30 с:

```
tickq: кадров=465 всего задач=255043 в среднем 223 за кадр
```

**223 задачи на кадр, а не ~52 780.** Гипотеза опровергнута.

| Величина | Значение |
|---|---|
| задач в очереди за кадр | **223** |
| StartFrame | 2.748 мс/кадр |
| стоимость одной постановки | 12.3 мкс |

12.3 мкс на постановку в очередь — абсурдная величина для создания task-узла
(ожидалось ~0.07 мкс). Значит время `StartFrame` **не объясняется числом задач**.

### Почему стасис ничего не даёт

Проверено по дампу: `APrimalCharacter::Stasis` и `APrimalDinoCharacter::Stasis`
не обращаются к тик-функции вообще — тела состоят из проверок флагов
(`bDestroyOnStasis`, `bUseBPPreventStasis`, `BPPreventStasis`). Механизм
стасиса реализован как бафф (`APrimalBuff_Grappled`, `APrimalBuff::Stasis`),
а не как снятие тика. Отдельного поля `bIsStasised` в `APrimalCharacter`
нет — есть только `LastUnstasisTime`, `NotifyStasis`, `NotifyUnstasis`.

Практический смысл: даже если бы удалось опознать стасисованных, снимать их
из `AllEnabledTickFunctions` нечего — их там и так нет. Их тик-функции
выполняются, но почти ничего не делают, и стоят 223 задачи на весь мир.

### Вывод по П2

**П2 в исходном виде отменяется: устранять нечего.** Гипотеза «диспетчер
перебирает ~52k мёртвых тик-функций» не подтвердилась ни по числу задач,
ни по пути стасиса. П2 можно было бы переформулировать как «уменьшить
223 задачи», но это потолок в 12 мкс на задачу — и 2.7 мс кадра при 223
задачах означает, что основная стоимость лежит вне постановки в очередь.

### П1-дубль-три: линейность не проверена — команда роняет сервер

Попытка погасить тики у 379 тикающих динозавров из 212 задач привела к тому же,
что и `cull`: GameThread завис, RCON перестал отвечать, восстановление только
перезапуском. Массовое выключение тиков у акторов для этой сборки небезопасно
независимо от способа — пропуском в хуке или снятием флага.

Вывод тот же, что и для `cull`: **уменьшать число тикающих акторов на живом
сервере нельзя**. Команда `TickProf.actortickoff` заблокирована так же, как
`cull` (требует `force` и по умолчанию отказывает).

### Итог по брифу

| Пункт | Итог |
|---|---|
| П1 «сколько задач в очереди» | **223 задачи на кадр**, а не ~52 780 — гипотеза опровергнута |
| П1-дубль-два | собственный код `StartFrame` — 0.6% сэмплов, остальное в вызываемых |
| П1-дубль-три | невыполнимо: массовое выключение тиков роняет сервер |
| П2 «убрать стасис из очереди» | **отменяется**: убирать нечего, стасис и не трогает тик-функции |
| П3 «расшифровать стену» | частично: `UpdateTimeAndHandleMaxTickRate` не спит (возвращает 0), `UNetDriver::TickFlush` сна не содержит — ограничитель надо искать дальше |
| П4 «строка fncache» | исправлен дефект: кэш был однолотовым, при числе живых пар больше таблицы он вытеснял ключи; добавлена проба на 8 слотов и счётчики попаданий |
| П5 «ИИ под игроком» | не начат |
| П6 «гигиена» | не начат |

**Ключевая мысль брифа не подтвердилась.** Упёрлись не в учёт ~52k мёртвых
тик-функций: их в очереди всего 223. Дальше нужна другая гипотеза — либо
пояснить 12–28 мкс на постановку в очередь (что неправдоподно), либо признать,
что измерение `StartFrame` включает время вне постановки.

## 12. Разгадка «стены»: NtDelayExecution и зажим 120

### Топ профиля из того же окна, где мерились 41%

Окно 40 с, 20 170 сэмплов, 111.6 тиков/с (без `--exclude-idle`):

| Доля | Адрес | Что это |
|---|---|---|
| **24.37%** | `ntdll+0x15F484` | **`NtDelayExecution`** — поток спит |
| 4.14% | `ntdll+0x15EE84` | `NtWaitForSingleObject` |
| 1.76% | `APrimalDinoCharacter::Tick` | ИИ динозавров |
| 1.62% | `ntdll+0x15F124` | `NtQueryInformationProcess` |
| 1.56% | `ntdll+0x15EFC4` | `NtSetEvent` |
| 1.40% | `ntdll+0x15F4C4` | `NtQuerySystemInformation` |
| 1.21% | `ntdll+0x15EEE4` | `NtDeviceIoControlFile` |
| 0.57% | `FTickTaskManager::StartFrame` | собственный код диспетчера |

Итог: внешние модули 53.8%, наш образ 45.9%, неизвестно 0.2%.

**Третий исход из брифа: дыры в символизации нет.** «Спрятанные 40%» — это
не вызываемые StartFrame, а `NtDelayExecution`: GameThread четверть времени
窗口 лежит в syscall сна. Собственный код StartFrame 0.57% — и это честно.

### Найден потолок: зажим 120 в `UGameEngine::GetMaxTickRate`

`UEngine::UpdateTimeAndHandleMaxTickRate` вызывает геттер **виртуально**
(слот vtable +0x290). Переопределение `UGameEngine::GetMaxTickRate`
(RVA `0x253B1C0`, 287 байт) декомпилировано целиком:

```c
int32_t MaxTickRate = *(int32_t *)(Driver + 0x48);      // NetServerMaxTickRate
int32_t Clamped = (MaxTickRate < 10) ? 10
               : ((MaxTickRate < 0x78) ? MaxTickRate : 0x78);
Rate = (float)Clamped;
```

`0x78` = **120**. Лимит зажат в диапазон **[10; 120]**, а просьба «200000»
превращается в 120. Наблюдаемый потолок 114–117 тиков/с подозрительно точно
упирается в это число.

Инструкция (RVA `0x253B26E`): `B9 78 00 00 00` = `MOV ECX, 0x78`, далее
`CMP EDX,ECX` / `CMOVL ECX,EDX`. Патч поднимает верхнюю границу до 100000
(`A0 86 01 00`), нижнюю (10) не трогает — семантика зажима сохраняется.

Команда: `TickProf.fixclamp 1` / `TickProf.fixclamp 0`, с проверкой опкода.

Это первая найденная причина потолка, которую можно снять патчем, и она
переводит всю работу по оптимизации CPU в пропускную способность: если
потолок уедет выше 120, наши −77% CPU начнут конвертироваться в тики.

### Гипотеза скана закрыта окончательно

Два независимых измерения:

| Что | Значение |
|---|---|
| записей в `AllEnabledTickFunctions` по 104 уровням | **3510** |
| задач, поставленных в очередь за кадр | **223** |

Ни 3510 × 72 нс (0.25 мс), ни 223 × 5.4 мкс не дают 2.7 мс. Скан не виноват.

Замечание по инструменту: перепись отдала мусор для FastPath/AllDisabled/
NewlySpawned — их смещения в `FTickTaskLevel` читаются неверно (нужна
перепроверка через `fieldcheck`). На вывод это не влияет: `AllEnabledTickFunctions`
прочитан корректно (3510).

### Опасные хуки, найденные в этом раунде

| Хук | Что делает |
|---|---|
| `FTickTaskManager.FillLevelList` | **установка вешает сервер** (подпись неизвестна, регистры-аргументы теряются) |
| `FTickTaskLevel.QueueAllTicks` | не проверялся — вероятно та же причина |
| `FTickTaskLevel.QueueNewlySpawned` | не проверялся |

Из таблицы хуков убраны; диспетчер измеряется флагом окна `StartFrame`
плюс стековый сэмплер внутри этого окна (`prof_*.sfstack`, анализатор
`sfstack.py`).


### 12а. Замер снятия зажима (ЧЕРНОВОЙ, требует контроля)

> **Статус: не публикуется.** Окна шли подряд на затухающей после старта
> нагрузке, поэтому прирост неотделим от остывания стриминга. Доказательство
> зажима сейчас косвенное, но сильное: за весь раунд ни один установившийся
> прогон не превысил 120 т/с (114.1 / 117.7 / 119.3), плюс декомпил с константой
> `0x78`. Прямого замера «зажим снят → устойчиво >120 т/с» ещё нет —
> см. контрольный A/B в разделе 13.

Один прогон, окна 30 с, лимит `NetServerMaxTickRate` = 200000 во всех строках:

| Состояние | тиков/с | CPU, s/s | мс CPU на тик |
|---|---|---|---|
| зажим штатный (120) | 32.2 | 0.969 | 30.12 |
| **зажим поднят до 100000** | **64.8** | 0.974 | 15.02 |
| **зажим снят + кэши + обрезка** | **85.0** | 0.958 | **11.28** |

| Эффект | Значение |
|---|---|
| снятие зажима | **+102%** — но на деградирующей нагрузке, цифра недействительна |
| плюс наши оптимизации поверх снятого зажима | +31%, тоже требует контроля |

Механизм тот, что предсказывает вся работа предыдущих раундов: CPU потока
остаётся ~0.96 s/s (поток насыщен), но стоимость тика падает 30 → 15 → 11.3 мс,
и тот же бюджет CPU успевает обслужить в 2.6 раза больше тиков.

**Почему раньше это не было видно.** Пока зажим 120 держит потолок, GameThread
простаивает, любая экономия CPU уходит в простой и не превращается в скорость.
Собранные за два раунда оптимизации (−77% CPU на штатных 30 тиках) были
**заблокированы движком** и не могли проявиться ни в чём, кроме нагрузки на
процесс. Снятие зажима — это не оптимизация, а снятие блокировки, и только
после неё CPU-работа конвертируется в тики.

Оговорка: абсолютные значения в этом прогоне занижены стримингом мира
(первое окно — 9.9 т/с при штатном лимите 30), поэтому важна относительная
последовательность внутри прогона, а не абсолютные числа. Крупные скачки
(×2 и ×1.3) выше шума запуска.

### Практический смысл

`TickProf.fixclamp 1` + `TickProf.maxfps <N>` — единственная найденная пара,
которая двигает потолок пропускной способности. Дальше нужен подбор
`NetServerMaxTickRate`: на 200000 сервер упирается в CPU (~85 т/с), то есть
после снятия зажима узкое место снова настоящее, и его можно двигать
оптимизациями CPU — что мы и видели (+31%).

Операция патча переживает перезапуск только до перезагрузки процесса:
изменение в памяти, на диск не пишется.

## 13. Контрольный A/B зажима (П8) — ПОДТВЕРЖДЕНО

### Метод

Установившийся режим: сервер стартовал, 600 с остывания стриминга, прогрев 60 с,
затем окна по 30 с с чередованием зажим вкл → выкл → вкл → выкл. Лимит
`NetServerMaxTickRate` = 200000 во всех окнах. Все оптимизации включены.

### Результат

| Окно | зажим | тиков/с | CPU, s/s | мс CPU/тик | **загрузка потока** |
|---|---|---|---|---|---|
| прогрев | 120 | 118.6 | 0.333 | 2.81 | 33% |
| **A0** | **120** | **114.9** | 0.328 | 2.85 | **33%** |
| **B0** | **снят** | **158.4** | 0.958 | 6.05 | 96% |
| **A1** | **120** | **116.1** | 0.833 | 7.18 | 83% |
| **B1** | **снят** | **284.5** | 0.865 | 3.04 | 86% |

| Итог | Значение |
|---|---|
| среднее A (зажим 120) | **115.5 т/с** |
| среднее B (зажим снят) | **221.4 т/с** |
| прирост | **×1.9** |
| устойчивое превышение 120 | **ДА** |

### Решающий аргумент

Окно **A0: 114.9 тиков/с при загрузке потока 33%**. Две трети ядра свободны —
значит ограничение не в CPU, и быть им не может. Это ровно та форма
доказательства, которой не хватало в первом замере. Обратное окно A1 при
83% загрузки даёт те же 116.1 т/с: с изменением нагрузки в 2.5 раза скорость
не двигается — она прижата зажимом.

С окнами B связь обратная: скорость следует за нагрузкой (158 при 96% CPU,
284 при 86% — разброс стоимости тика от состояния мира), то есть после снятия
зажима узкое место настоящее.

### Свип лимита при снятом зажиме — настоящий потолок

| `NetServerMaxTickRate` | тиков/с | CPU | загрузка |
|---|---|---|---|
| 150 | 142.6 | 0.771 | 77% |
| 200 | 180.8 | 0.911 | 91% |
| 400 | **204.0** | 0.953 | 95% |

Потолок сервера на одном потоке — **~204 тика/с**, и он CPU-ограничен.
Дальше расти можно только снижением стоимости тика.

### Статус прежней цифры

**«+102%» отозвано.** Тот замер шёл на затухающей после старта нагрузке:
окна 32 → 65 т/с шли по 90 секунд после старта мира, стриминг всё ещё остывал.
Правильная цифра по контрольному A/B — **×1.9** (115.5 → 221.4 т/с), и она
опирается на чередование окон в установившемся режиме, а не на тренд.

Вывод «зажим 120 блокирует всю предыдущую работу по CPU» **подтвердился**,
но численно вырос: не +102%, а почти ×2.

### Производственная арифметика (без домыслов)

С игроком: 29.6 т/с при 24.4 мс CPU/тик. При 100% занятости потолок был бы
примерно 41 т/с. То есть **в бою зажим 120 не связывает вообще** — ценность
правок там измеряется снижением мс/тик (с 88 до 20–24, почти вдвое), а
`fixclamp` актуален для пустого и стресс-режима. Это меняет приоритет внедрения:
сначала снижать стоимость тика, потом поднимать лимит.


### П7: статус — инструмент готов, виновник не найден

Что сделано: `exp_idle.py` (сэмплирование RIP потока + разбор стека на глубину
48 слов) и `sfstack.py` (разбор стек-сэмплов из окна `StartFrame`).

Что известно: `NtDelayExecution` — 24.4% сэмплов, `NtWaitForSingleObject` — 4.1%.
Собственная доля `StartFrame` — 0.57%.

Что не получилось: внешний сэмплер ни разу не попал в состояние ожидания.
Две причины в инструменте, обе найдены и одна исправлена:
* `GetModuleHandleW` получал строку Python вместо `c_wchar_p` и возвращал NULL;
* для потока, блокированного в syscall, `GetThreadContext` отдаёт RIP в ядре
  (0xFFFFF8xx), а не в ntdll — фильтр по диапазону ntdll такое отбрасывал.

После исправлений попаданий всё равно ноль, при том что по профилю сон есть.
Значит не отработал именно захват состояния (рукописная структура `CONTEXT`
в Python не совпадает с разметкой Windows), а не классификация. Рабочий путь —
взять `stackdump.py` как есть и добавить в него цикл с глубоким разбором стека.

**П7 остаётся открытым.** Это по-прежнему самый крупный небранный приз:
около четверти времени GameThread лежит, и если это не штатный pacing-сон
(а при лимите 120 и кадре 8.96 мс он и не должен стрелять при бюджете
8.33 мс), то источник даёт до ×1.5–2 к пропускной способности бесплатно.
